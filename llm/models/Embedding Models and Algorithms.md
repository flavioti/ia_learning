# Embedding Models and Algorithms

Most used models, algorithms and frameworks to generate and search embeddings. An embedding model does **not** need to be a generative LLM: most are smaller **encoder** models, and many run locally.

> [!warning] Same model for insert and query
> Vectors generated by different models are not comparable. Use the same model (and version) to index the data and to embed the query. This applies to local and API models. See [[top-k]].

## 1. Dense embedding models (most common)

One vector per text, semantic, compared by similarity. This is the default for [[RAG]] and semantic search.

| Model                    | Type             | Dimensions | Multilingual   | Runs local? | Typical use                                                   |
| ------------------------ | ---------------- | ---------- | -------------- | ----------- | ------------------------------------------------------------- |
| `text-embedding-3-small` | API ([[OpenAI]]) | 1536       | Yes            | No          | Fast start, low cost                                          |
| `text-embedding-3-large` | API ([[OpenAI]]) | 3072       | Yes            | No          | Higher quality                                                |
| Cohere Embed             | API              | ~1024      | Yes            | No          | Multilingual search                                           |
| Voyage AI embeddings     | API              | ~1024      | Yes            | No          | Retrieval-focused quality                                     |
| `bge-m3`                 | Open-source      | 1024       | Yes            | Yes         | Multilingual, dense + sparse + multi-vector                   |
| `multilingual-e5`        | Open-source      | 768 / 1024 | Yes            | Yes         | Multilingual retrieval (needs `query:` / `passage:` prefixes) |
| `all-MiniLM-L6-v2`       | Open-source      | 384        | Mostly English | Yes         | Small, fast, prototypes                                       |
| `nomic-embed-text`       | Open-source      | 768        | Mostly English | Yes         | Long context, via [[providers/Ollama]]                                  |
| `mxbai-embed-large`      | Open-source      | 1024       | Mostly English | Yes         | Good quality, via [[providers/Ollama]]                                  |

**Where they run**

| Option | Notes |
|--------|-------|
| **Provider API** | High quality and no infrastructure, but has cost per token and data leaves your environment |
| **Open-source, local (CPU or GPU)** | Best cost-benefit and keeps data inside the environment |
| **Behind a local API** | The same open-source models served by [[providers/Ollama]] or [[vLLM]] |

## 2. Sparse / lexical algorithms

Match words, not meaning. Good for keywords, bad for semantics.

| Algorithm | How it works | Strength | Weakness |
|-----------|--------------|----------|----------|
| [[Okapi BM25\|BM25]] | Term frequency, inverse document frequency and length normalization | Exact terms, codes, names, SKUs | No synonyms, no semantics |
| TF-IDF | Term weight by frequency and rarity | Simple, cheap, no model | Same as BM25, usually weaker ranking |
| SPLADE | Learned sparse vectors (model expands terms) | Lexical precision with some semantics | Needs a model |

## 3. Multi-vector and other forms

| Form | Example | How it works | Trade-off |
|------|---------|--------------|-----------|
| Multi-vector | ColBERT | One vector per token, late interaction | More precise, higher storage and cost |
| Word embeddings | word2vec, fastText | One vector per word, no context | Legacy, weak for sentences, rarely used today |
| Cross-encoder (reranker) | `bge-reranker`, Cohere Rerank | Scores query and document together | Slow, used to rerank the top-k, does not generate embeddings |

## 4. Similarity metrics

| Metric | pgvector operator | Notes |
|--------|-------------------|-------|
| [[cosine similarity\|Cosine]] | `<=>` | Most common for text embeddings |
| Euclidean (L2) | `<->` | Sensitive to vector magnitude |
| Inner product | `<#>` (negative) | Equals cosine when vectors are normalized, fastest |

## 5. Vector search and index algorithms

| Algorithm | Type | Notes |
|-----------|------|-------|
| Exact (brute force) | Exact | Scans every vector, fine for small datasets |
| HNSW | Approximate (graph) | Most common index, fast with high recall, uses more memory |
| IVFFlat | Approximate (clusters) | Faster to build, needs tuning of lists and probes |
| [[Hybrid Search]] | Combination | BM25 + dense vectors, merged with RRF or weighted scores |

## 6. Local example with `sentence-transformers`

```python
from sentence_transformers import SentenceTransformer

model = SentenceTransformer("BAAI/bge-m3")   # runs local, no API

# At insert time
doc_vectors = model.encode(product_descriptions, normalize_embeddings=True)

# At query time (SAME model)
query_vector = model.encode("lightweight laptop for travel", normalize_embeddings=True)
```

## 7. How to choose

| Situation / criteria | Choice |
|----------------------|--------|
| Start fast, no infrastructure | `text-embedding-3-small` |
| Privacy / compliance (LGPD/GDPR), local | `bge-m3` or `multilingual-e5` |
| Catalog not in English | A **multilingual** model (`bge-m3`, `multilingual-e5`) |
| Prototype, low resource | `all-MiniLM-L6-v2` |
| Low latency | A small local model answers in milliseconds on CPU |
| Volume and cost | Local has fixed infrastructure cost, API charges per token |
| Exact codes and names matter | Add BM25 with [[Hybrid Search]] |
| Need better ranking of the top-k | Add a cross-encoder reranker |
| Quality | Large APIs usually win by a small margin, modern open-source models come close |

To verify the quality of the chosen model, see [[Embedding Evaluation]].

## 8. Attention points

- **Column dimension**: `vector(N)` must match the model output (e.g. `bge-m3` = 1024, `all-MiniLM-L6-v2` = 384).
- **Required prefixes**: some models (E5 family) expect `query:` and `passage:` before the text.
- **Changing the model** means re-embedding the whole dataset.
